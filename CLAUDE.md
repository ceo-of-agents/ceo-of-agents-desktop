# CEO of Agents (desktop app)

A Mac desktop app to run a ceo-of-agents micro-org (an AI-agent organisation kept in a git folder, its "hq"): one continuous thread with the chief of staff, temporary department chats that end with a handoff, the "Waiting on you" and "Initiatives" panels read from the org's hq, and an hq health indicator. It drives the user's own, unmodified Claude Code CLI (`claude -p`, stream-json).

This file owns the repo's technical facts. Keep it current when the stack, commands or conventions change.

## Stack
- Electron 45, TypeScript (strict), React 18 for the renderer, plain CSS.
- esbuild bundles four entry points (`scripts/build.mjs`): main process, preload, renderer, and the MCP permission server.
- Runtime dependencies besides React: `yaml`, and `react-markdown` with `remark-gfm` (assistant messages render GitHub-flavored Markdown; no raw HTML, https links only, images never loaded; rules in `src/renderer/markdown-safety.ts`).
- Tests: vitest (node environment). Lint: eslint 9 flat config with typescript-eslint, plus `tsc --noEmit`.

## Commands
- `npm install`
- `npm start`: build and launch the app.
- `npm test`: unit tests.
- `npm run package:mac`: build `out/CEO of Agents.app` (ad-hoc signed only) and `out/CEO of Agents-<version>.dmg` (unsigned). Local build, nothing is published. Needs the Electron binary (`node node_modules/electron/install.js` if `node_modules/electron/dist` is missing).
- The "Mac release" workflow (`.github/workflows/release-mac.yml`) runs the same build in CI; see "Release flow".
- `npm run lint`: eslint and type check.
- `npm run check`: lint and tests (run before every PR).

## Layout
- `src/main/`: main process, the supervisor. It is the only place that spawns processes.
  - `claude/`: `activity.ts` (a tool call as one plain-language line for the thread), `artifact-actions.ts` (an `Artifact` call as an action, a target and a plain sentence, plus the safe actions), stream-json parser, `ClaudeSession` (one long-lived `claude -p` per thread, no queue: every message is written at once), permission broker, thread log, session store.
  - `hq/`: hq parsing (the org chart in `org-chart.ts`: org.yaml plus the frontmatter of `.claude/agents/*.md`, never throws, `error` and `problems` on the `OrgChart`; org.yaml, the CLAUDE.md routing table, `company/state.md`, the optional `company/todo.md` (schema `todo/1`: its open T items join "Waiting on you" as `kind: 'T'`, `action: 'do'`, with an optional `status`), the cards of `company/decision-queue.md` (`decisions.ts`, `parseDecisionCards`: context, options, recommendation, `proposed_by`, `escalate`; a D item gets `card`, and `options` only when the card lists two or more; `parseDecisionOptions` is a view of it), `initiatives/*/status.md`), discovery, the app's org registry, file watching. All parsing lives here, with tests on real samples.
  - Parent and child items in the lists (plugin schemas `state/1` and `todo/1`, "Parent and child items"; `scanItems` in `parse.ts` serves both files): a child is a line of exactly two spaces and `- ` with the item pattern under the nearest top-level parsed item and gets `parent` (that item's code); an orphan, a child under an unparsed line and a wrongly indented line with the item pattern stay top-level items (nothing disappears); a two-space `- ` line without the pattern still joins the line above; the kind `{wait}` is `action: 'wait'` (a group heading: no buttons, not counted; `countAsks` in `src/shared/waiting.ts` is the one count, used by the badge, the org summary, the header and the focus menu).
  - Org icon: `company/icon.png` in the hq, a fixed path with no org.yaml key (`hq/org-icon.ts`). Setting it is split so decoding stays off the main process: `pickOrgIcon` (main) opens the dialog (PNG, JPEG, WebP) and `readOrgIconSource` opens the file non-blocking and checks the open descriptor (`fstat`: a regular file, so a FIFO, device or folder is `notAFile` and never read; 10 MB cap; PNG/JPEG/WebP by first bytes) and returns the bytes as base64; the renderer (`renderer/org-icon-actions.ts`, `renderIconPng`: `createImageBitmap` decodes off the main thread and reads WebP, which Electron's `nativeImage` cannot on macOS; centre crop, 256 x 256 canvas, PNG; sources over 100 million pixels refused) sends the PNG back through `saveOrgIcon`, and main does not trust it: base64 text over the cap is refused before decoding, then `writeOrgIcon` checks the 8-byte PNG signature, at most 1 MB and an IHDR of exactly 256 x 256, and writes atomically (no link on the path below the hq). `readOrgIcon` and `orgIconStamp` open with `O_NOFOLLOW | O_NONBLOCK` after the path checks and read from the open descriptor after an `fstat` (regular file, size cap), so a link or FIFO swapped in after the checks fails; served to the renderer as a `data:` URL (`getOrgIcon`) and cached by `OrgSummary.iconStamp` (`org-icon-cache.ts` keeps one entry per org: a new stamp evicts the previous one); the hq watcher (`icon` change) refreshes the `orgs` event. It replaces the initials in the rail and the Settings org tile. Entry points, one code path (`setOrgIcon`, `removeOrgIconNotice`): Settings > General and the right-click menu of the org's rail item (`OrgRailMenu.tsx`: "Set icon…", and "Remove icon" only when the org has an icon; the result is a toast). The app never commits or pushes it, and keeps nothing in userData.
  - `tips/`: contextual tips (plugin schema `tips/1`, `schemas/tips.md`, plugin 0.21.0+). `tips.ts` is pure: `parseTips` (never throws, skips invalid tips), `conditionHolds`/`whenHolds` (keys `pending`, `days_since_last_session`, `days_since_last_brief`, `hq_behind_plugin`, `file_missing`, plus the app-side `always` and `org_icon_missing`; `chat` and any unknown key hide the tip), `fillTemplate` (`{codes}`, `{decision_code}`, `{cos_name}`; `{department}`, `{initiative}`, `{repo}` and unknown names hide the tip), `textInLanguage` (the `translations` entry for `language.chat`, else English), `selectTip` (not dismissed, not `pending`, `since` met by the hq's `framework_version`, condition true, placeholders filled; one at a time, day of the month mod candidates like the CLI). `facts.ts` reads the facts from the open org's hq at display time (state.md, briefs, the setup record, org.yaml, file existence, the icon). `plugin-tips.ts` reads `tips/tips.yaml` of the installed plugin (folder found by `findPluginDir`, as the setup wizard does; `COA_PLUGIN_DIR` in development; cached 2 minutes; a plugin without the file gives no plugin tips), `app-tips.ts` is the app's own list in the same shape (texts in en.json, `tips.app.*`), `service.ts` ties them together (`OrgManager.getTips`, `dismissTip`; IPC `getTips` returns the applicable, not dismissed tips in display order, the day's pick first, `selectTips`; `dismissTip`). Dismissals (`tipsDismissed`) and the off switch (`tips`, Settings > General) live in `<dataDir>/orgs/<orgId>/settings.json`, never in the hq; `tips.show` and `tips.dismissed` of the hq's org.yaml are honored read only.
  - Voice file (plugin `voice/1`, `schemas/ceo-voice.md`, aligned with ceo-of-agents 0.22.0): the path is `ceo.voice` of org.yaml, else `company/ceo-voice.md`, which the plugin uses with no activation step (so there is no `active` flag and the app never edits org.yaml), read and written by `hq/voice.ts` (`readVoice`, `writeVoice`: inside the hq, no link on the way, 256 KB, atomic; invalid `ceo.voice` is an error, never a fallback write; a path that is not a `.md` file is refused to read and to write, `notMarkdown`; `readVoice` returns a version token, the sha256 of the content or `missing`, `writeVoice` takes it back and re-reads right before the rename, so a file changed on disk since it was loaded, or one that appeared after a missing load, is a `conflict` and nothing is written: the editor shows the error with a Reload button and keeps the new token after a save), the same pattern as the org icon; the app never commits or pushes it. The pure side is `shared/voice.ts`: `parseVoice`/`serializeVoice` keep every line (round-trip safe), `voiceModel`/`applyVoiceModel` edit only Base, the `###` entries of Channels and Audiences (unedited entries, the how-to block, HTML format comments and unknown sections stay byte for byte), `voiceTemplate` is the plugin's 0.22.0 template, used when the hq has no file. Settings > "Your voice" (`SettingsVoice.tsx`, `voice-logic.ts`) edits it and sets `last_updated`.
  - Draft in every chat: a "Draft" button in each chat's composer foot opens `DraftForm.tsx` (channel and audience from the voice file, free text when it lists none, the message to answer) and sends one message to that same chat (`buildDraftPrompt`: the chief of staff is asked to use the `draft-as-ceo` skill; a department cannot load skills, so it is pointed at the voice file's "How to use this file" block). The message starts with the fixed line `draft.msg.head` and asks for the draft "in the plugin's draft format" (plugin 0.22.0, `schemas/ceo-voice.md`: exactly one fenced block with no info string, a longer fence when the draft has backticks, mail as `Subject: <subject>`, a blank line, the body, then one short line naming channel and audience) and adds only a short fallback sentence for older plugins; `draftResults` gives Copy buttons (`DraftCopy`) to the assistant message that follows such a request and holds a finished block of 3 or more backticks with no info string (the closing fence at least as long as the opening; `firstFencedBlock`), and a block whose first line is `Subject: <subject>` followed by a blank line splits into two copies (otherwise one). Nothing is sent outward. The skill's "Captured corrections" has no detectable form (one plain sentence), so there is no yes/no card yet.
  - `system/`: `exec.ts` (the one-shot command runner and PATH for Finder-launched apps), Claude Code location and version check, sign-in flow, plugin status, install and update, git and Terminal helpers. `app-update.ts` (`AppUpdater`, app-wide): the "Update app" button in the top bar; see "Release flow".
  - `git/`: hq health, sync, automatic push (quiet: nothing in the thread; fetches first, treats a remote that has HEAD as success, rebases once on non-fast-forward, reports a failure only after 3 consecutive attempts, with a "Try again" in the health popover; a conflict between the hq and GitHub shows "Ask {cosName} to fix it", which sends the chief of staff tab a request).
  - `org/`: per-org supervisor (CoS thread, department tabs) and the org manager.
    - Department liveness (`org/dispatches.ts`, `DispatchTracker`, one per org): the streams of the CoS thread and of the department tabs (`ClaudeSession` 'stream' events: Agent `tool_use`/`tool_result`, `system/task_started`, `task_progress`, `task_updated`, `task_notification`, and sub-agent lines with `parent_tool_use_id`, counted as activity only, never content) give each Agent call a state: running, done, failed, stopped, or unknown (that thread's process ended, or the app restarted while it ran). Each item belongs to a thread (`handle(ev, owner?)`, `sessionExited(threadId)`, `hasRunningBackground(threadId?)`) and an event touches only its own thread's items. A tab's own sub-agents are attributed "<persona> → <agent>" (`Dispatch.by`), shown under that department, with no toast and no macOS notification; they count for the run guard like the CoS's (`forceStop` writes the "was stopped by" line in that tab's thread), are stopped and dropped when the tab ends (`dropThread`), are acked once that tab is the shown thread, and closing a tab that has some running asks first. Kept in `<dataDir>/orgs/<orgId>/dispatches.json`; the renderer gets `dispatches` and `dispatch-ended` events and acks ended ones once the thread that made them has been seen (`renderer/dispatch-logic.ts`, `useDispatchAck.ts`; a dispatch seen running again forgets its old ack state). The macOS notification for an ended dispatch names only who and how it ended (`endedNotificationText`), never the task description, since it can show on a locked screen. Agents of the CoS that are not a department in org.yaml (workers, helpers) show under the CoS. The CoS's report on a finished background agent comes as an aside (a turn Claude Code starts by itself); `ClaudeSession.reportPending` (thread state `reportPending`) is true from the top-level `task_notification` to that report's result, and a finished dispatch is not acked before it ends. Only the thread's own process exit (or one it is stopping) turns running dispatches into unknown; an empty or leftover result (`num_turns` 0) does not. A SendMessage resume of an agent is a new `task_started` with the same `task_id` (the agent id, kept as `Dispatch.agentId`) and the SendMessage `tool_use_id`; its sub-agent lines keep the original Agent id and add `agent_id`. The tracker revives the dispatch that has that agent id (any state, also after an app restart), or, for an agent it does not know and a SendMessage seen in that thread, creates one whose id is the SendMessage id; any other unknown `task_started` is ignored, and the answer to a SendMessage never ends a dispatch. Shapes checked with Claude Code 2.1.328 (fixtures `test/fixtures/claude/dispatch-*.jsonl`: `dispatch-resume*.jsonl` recorded and scrubbed, `dispatch-tab.jsonl` built by hand in the same shape).
    - Confirm before stopping work (`org/run-guard.ts`, `RunGuard`; the dialog is the injected `ask`, a native `dialog.showMessageBox` in `index.ts`): `OrgSession.runningItems` lists the org's running dispatches and, while the chief of staff replies (or its report turn is about to start, `Thread.awaitingReport`), one `cos-turn` item. An action that would end them goes through `guard.run(scope, label, fn)`: nothing running means no dialog; else "Wait and do it when they finish" (queued, a system line in the thread and a notice, run when the scope has no items left), "Stop them and continue" (`OrgSession.forceStop`: dispatches become `stopped`, one "was stopped by" line each in the chief of staff thread, the process ends and the messages it had not answered end with it) or "Cancel". Org-scoped actions (Update, Apply now, Install plugin; the IPC handlers in `ipc.ts`) look only at their own org; quit (Cmd+Q, the last window closing) looks at every org and groups the lines by org; macOS shutdown (`powerMonitor` `shutdown`) asks nothing and force-stops with the label "Shutdown". Every way the app ends goes through `QuitCoordinator` (`src/main/quit.ts`): the department chats' handover check (`org/close-check.ts`), then the run guard, then one shutdown; Cancel at any step leaves the app as it was, a queued Quit runs the whole sequence again when the work ends and wins over other queued actions, and the guard asks per scope (an org's dialog does not swallow Cmd+Q). There is no close/remove-org action and no app-wide restart yet: a new one must go through the guard too.
    - The top bar has one "Update" per org (`OrgManager.updateOrg`, steps in `org/update-org.ts`): when the plugin is behind (and `COA_PLUGIN_DIR` is not set) it updates the plugin and restarts the org's chats, then, if the hq's `framework_version` is behind the installed plugin, sends the CoS thread `cos.msg.applyHqUpdate` (the click is the user's OK for the `hq-version` migrations) and waits for that tagged turn to end (or for the hq to stop lagging), then re-reads the status (once more after 3 s when the hq still lags, before any error). One run per org at a time. Each step shows in the top bar's plugin label (`PluginActionState.step`); every path ends with one `running: false` emit, with an error text when the plugin or hq version was not applied.

The Mac app menu is spelled out (About, "Check for Updates…" through an injected click handler that `index.ts` wires to `AppUpdater.checkNow` and a dialog, Services, Hide, Quit); other platforms get it under Help. View > "Waiting on you: focus view" (Cmd+Shift+F, `focus-waiting` event) is enabled only while an org is open and something waits: the renderer tells main through `CoaApi.setWaitingFocusAvailable` (menu rebuilt only when the value changes). Cmd+W is "Close Tab" (sent to the renderer as a `menu` event); the window's own close is Cmd+Shift+W; Cmd+Shift+O is "Org Chart" (toggles the Org chart view, `menu` event `org-chart`); Chat > New Session (Cmd+Shift+N) asks for a new chief of staff session (`new-session` event).

- `src/mcp/permission-server.ts`: a tiny local MCP server, launched by Claude Code through `--mcp-config` and `--permission-prompt-tool`, that forwards each permission prompt to the main process over a unix socket.
- `src/shared/questions.ts`: Claude Code's `AskUserQuestion` input parsing and answer building (pure; `parseQuestions`, `buildAnswers`, `isQuestionRequest`).
- `src/preload.ts`: exposes `window.coa` (the `CoaApi` in `src/shared/types.ts`).
- `src/renderer/`: the UI. It never spawns processes and only calls `window.coa`.

Clicking the text switches to the org's chief of staff chat (closing the chart or leaving a department tab), puts the phrase in its composer draft (an empty box becomes the phrase; typed text is kept and the phrase is appended on a new line, `phraseInsertion`) and never sends. `App` passes ThreadView an `insertRequest` (nonce plus selection); ThreadView focuses the box and selects the `...` part (else the cursor at the end), then calls `onInsertDone`. Two buttons: "Got it" dismisses the tip for good in this org (same per-org persistence as before) and shows the one after it in the list (wrapping; the box disappears when none is left); "Next tip" shows the next applicable tip without dismissing and wraps around (`nextTip`, `afterGotIt` in `tip-logic.ts`), hidden when only one tip applies.

## How the app runs Claude Code
- Base command, cwd = the hq: `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --permission-mode <org's mode> --effort <org's effort> [--model <model>] --permission-prompt-tool mcp__coa__permission_prompt --mcp-config <app server> [--strict-mcp-config] --setting-sources project,local [--settings <deniedMcpServers json>] --allowedTools "Skill(ceo-of-agents:*)" <hq allow rules> [--disallowedTools <hq, user and forbidden-connector deny rules>]`; department tabs add `--agent <agent>`. The child env also sets `CLAUDE_CODE_ARTIFACT=1` (unless the user turned artifacts off, see "Artifacts"). `--effort` is always passed; `--model` only when one resolves (CoS: the CoS model; a tab: its department's model, see below).
- Connectors: normally no `--strict-mcp-config`; a chat loads the MCP servers Claude Code loads in the hq folder (claude.ai connectors, the hq's `.mcp.json`, local-scope servers). - Turns (no app-side queue): every message is written to Claude Code at once, with a `uuid` that `ClaudeSession.send` returns; `ClaudeSession` keeps the messages not answered yet (`pending`, in write order) and follows each one by the `command_lifecycle` events (`queued`, `started`, `completed`) that carry its uuid. The thread (`Thread`) keeps the same list (`unanswered`): `busy` means it is not empty, `ThreadState` has no queued count, and a new session or a settings restart happens only from idle (nothing unanswered written). A `turn-end` carries `uuids`, the messages that result answers: those Claude Code `started` or `completed` (a message written mid-turn during a tool call is absorbed into the running turn: one result answers both, `num_turns` 2; one written during streamed text or at the result gets its own turn with its own init and result). Without lifecycle events a result answers the oldest message. Messages left with no lifecycle state after such a result (absorbed by an older Claude Code) are answered with an empty, non-error turn end after `ABSORBED_MS` (15 s) of a silent stream with no turn open (`absorbedMs` option); a null state counts as `queued` once any message has a state. The thread puts the reply after the answered messages and passes the whole batch to its listeners (`TurnResult.sent` is a list: a tag listener matches if any message of the batch has its tag). Claude Code also starts turns on its own (a background task or agent finished; on `--resume`, a leftover notice with an empty result), so a result while every pending message is still `queued`, or an empty one of no model call (`num_turns` 0), is held: `started` for a message makes it an `aside` (shown as its own assistant message, never the end of a message's turn; its text is not streamed as the reply), `completed` makes it the message's own, and any sign of the model working (text, a tool, a stream event) drops a held empty result. After `HOLD_MS` (5 s) of a silent stream, with no turn open (an init since the last result) and no message `started`, a held result counts as the oldest message's, so nothing stays busy for ever; a process exit during a turn ends every pending message with one error `turn-end` carrying all their uuids, and releases a held result as an aside. An aside in an idle chat raises a notice and a desktop notification (`notice.wroteOnOwn`); releasing a held result as an aside also emits `own-turn-end`, so the thread drops the tool calls seen so far (a handover turn sees only its own writes). Interrupt, forced stop and a crash end every unanswered message. - The CoS thread is one thread in the UI with its full log, but the Claude Code session behind it is not resumed across app runs. A new session is `makeSession(null)` (no `--resume`) and nothing extra is sent: the hq's CLAUDE.md makes the chief of staff run its session-start routine on the first message of every session. One starts at the first message after: the app opened; `newSessionAfterMinutes` of inactivity (no event of the live session; 0 = never); the last activity was on an earlier local day (a conversation going past midnight is not cut); or Chat > New Session (`Thread.requestNewSession`, through `newSession` in the API: it stops and sends nothing, only the next message from idle starts the session). It is decided only in `enqueue`, for a message sent from idle (nothing unanswered): a message sent while others are unanswered continues the session they run in. While background work lives in the process or a report is pending (`holdRestart`, plus `awaitingReport`), the new session waits (one system line) and starts with the first message from idle after it. Each new session adds a `session` divider entry before the message ("New session, read from hq at <time>"). Two kinds: those reasons give a NORMAL new session (nothing extra is sent); a second, size trigger gives a CONTINUED one (the chat goes on). Size trigger: after every `result` of the live session (a turn end or an aside) the parser reads the context size with no extra model call (`contextTokens` of the `result` event in `stream.ts`, `ClaudeSession` emits it as a `context` event): `usage` of the result is SUMMED over all model calls of the turn and overstates the context (checked with Claude Code 2.1.327, `test/fixtures/claude/write-permission.jsonl`), so it takes the last element of `usage.iterations` (the last model call only): input + cache read + cache creation tokens; fallback the same sum from the last top-level assistant message of the turn; else null (no event). The thread counts results per session (`sessionTurns`, reset when a new session starts, not on a technical restart) and sets `renewForSize` when the size reaches `renewSessionAtTokens` on the 2nd result or later (the first result never triggers, so a session whose start alone passes a low limit cannot renew on every message). `renewSessionAtTokens` (50000, 100000, 150000, 200000, 400000 or 0 = never; default 100000; invalid ignored) lives in the same `settings.json` as `newSessionAfterMinutes`. In `decideFresh` a normal reason wins over `renewForSize`; only when none is due does `renewForSize` start a continued session (same hold rule; starting either kind clears both flags). A continued session is `makeSession(null)` too, but its first message is built in `src/main/org/continuation.ts` (`continuationText`): the line `CONTINUATION_MARKER` = `[ceo-of-agents] Continued session: read the hq silently, give no status recap, then answer the new message. The last messages of this chat follow verbatim.`, a blank line, then one block `--- <author>, <HH:MM local> ---` + the text for each of the last 6 user and assistant entries of the log (`recentMessages`, verbatim, oldest first, taken before the new message's entry is written; images only: `(image)`), separated by blank lines, then `--- New message ---` and the message (after any "!" command output, which is part of the wire text). The thread shows only the user's own text; the divider carries `continued: true` ("New session (continued), read from hq at <time>"). The ceo-of-agents plugin recognises the marker as the first line of the first message, so the text changes only together with the plugin. Technical restarts inside a run (process exit, `restart()`, `interrupt`, a changed model, effort or rule) still resume the current session id; a stale `--resume` starts a new session with a divider. `newSessionAfterMinutes` (15, 30, 60, 120, 240 or 0; default 30; invalid ignored) lives in `<dataDir>/orgs/<orgId>/settings.json` next to `autoPush`. - Department chats: one open chat per department (`startTab` returns the open or handing-over one instead of starting another; chats with different departments run side by side). A chat ends for good when it is closed or hands over, both through `OrgSession.endTab`: status `closed`, its process stopped (stdin closed, SIGTERM, then SIGKILL, sent to the whole process group so tool children die too; cut off at once when busy; the thread is disposed and never respawns), its permission cards denied and its session id removed from the session store (the process is stopped first, so a failing write never leaves it running). "Handed over" means `TabInfo.notePath` is set: by the Hand over flow, or by a turn end that finds a note (`OrgSession.detectNote`). No rule proposal, never auto-allowed (not even by the in-run "Always allow" memory), no timeout; `respond` refuses allow/always on a question the app can show. The desktop notification (`questionNotice`, `src/main/claude/question-notice.ts`) says a chat waits for an answer, without the question text. A malformed input (for example 5 questions, more than 8 options, duplicate labels) falls back to a reduced permission card with one button, "Ask in the chat instead", and `respond` then denies on any decision with `The app could not show this question; ask it again in plain text.`, so Claude asks in plain text; the fallback is never auto-answered and has no timeout either.
- Plan usage: the only source is the `rate_limit_event` Claude Code writes in stream-json after each model call (checked with 2.1.327: `rate_limit_info.unifiedWindows` with `five_hour` and `seven_day`, each `utilization` 0..1, `resetsAt` epoch seconds, `status` `allowed`/`allowed_warning`/`rejected`; per-model weekly windows `seven_day_<model>` are read the same way when present). `parseRateLimitInfo` (`src/shared/usage.ts`) keeps only the windows and drops every other field (overage, billing). `UsageTracker` (`src/main/claude/usage-tracker.ts`, one per app on `OrgManager.usage`: every chat runs on the same sign-in) keeps the last value in memory (`CoaApi.getUsage`, `usage` events) and sends one notice and desktop notification when a window reaches 80 % (or `allowed_warning`) and when it is reached, once per window period. The top bar shows one chip per window with the used percent and the time left to its reset ("Session 13% · 2 h 5 min", "Week 41% · 3 d 4 h", `span()` in `src/renderer/usage-view.ts`; the 5-hour window is "Session" as in Claude Code's `/usage`, never a label that reads like a duration; no countdown when the reset time is unknown, "Session ?%" once it has passed), reset times in the tooltip, "Usage unknown" until the first reply. The countdown moves every 30 s on the renderer's clock, with no new reading. A failed result with `api_error_status` 429, or after a `rejected` event, ends the turn with `TurnEnd.limit` and the thread shows "Usage limit reached (…): it resets at …" instead of the raw error. While every chat is idle, `UsageRefresher` (`src/main/claude/usage-refresh.ts`, `OrgManager.usageRefresh`) keeps it current with `claude -p /usage`, a local command in print mode (checked with 2.1.327: `local_command: "usage"`, `num_turns: 0`, `duration_api_ms: 0`, empty `modelUsage`, so no model call and no plan usage spent). It runs with `--output-format json --no-session-persistence --setting-sources '' --strict-mcp-config --tools ''` from the temp folder, every 5 minutes when no chat is running and the last reading is over 4 minutes old, and when the user clicks the usage indicator (`CoaApi.refreshUsage`); only from Claude Code 2.1.327 on, and it turns itself off for the app run if a result ever shows a model call. `parseUsageText` (`src/shared/usage.ts`) reads only the `Current session` / `Current week (…)` lines (percent and reset time, in the time zone the line names) and drops the rest of the text (what contributes to usage) unread. The tooltip shows each reset with a countdown and the age of the reading; a window whose reset time has passed shows `?` until the next reading. The app never calls the API itself or reads credentials or `~/.claude.json` for it.
- Commands with "!": a draft starting with `!` is not sent to Claude Code. `CoaApi.runCommand(orgId, threadId, command)` reaches `OrgSession.runCommand`, which refuses an empty command, one over 2,000 characters or holding control, bidi or zero-width characters, and a second one in the same chat; then a native dialog (`ipc.ts`, Cancel is the default) shows the exact command, the hq folder and any deny rule that covers it. On Run, `src/main/system/user-command.ts` runs it with the user's `$SHELL -c` in the hq folder (the renderer cannot name a folder), stdin closed, in its own process group: 2-minute timeout, 30,000 characters of output kept, Stop from the thread. It ends as a `command` entry (marked as run by the user) and its output goes before the text of the chat's next message, in Claude Code's own form (`<bash-input>`, `<bash-stdout>`, `<bash-stderr>`); `claude -p` with stream-json input has no bash mode of its own. Not kept across an app restart until that message.
- Process ledger: every `claude -p` the app starts runs detached in its own process group, so a crash, a force quit or a signal to the main process would leave it running under launchd. `ProcessLedger` (`src/main/claude/process-ledger.ts`, one per app, created in `index.ts`, passed through `OrgManager` deps to `OrgSession`'s `spawner`, a `trackedSpawner` over `spawnProcess`; `session.ts` is not involved) records each child in `<dataDir>/claude-processes.json` (atomic write; per line only `pid`, `orgId`, `hqPath`, `appPid`, `spawnedAt`: never arguments, env or tokens) and drops the line when it exits. Ending: `OrgManager.shutdown()` calls `ledger.close()` first (a closed ledger refuses to spawn, so a thread pump mid-start fails its turn instead of starting a new process), then `stopAll`, then `killAllSync('SIGKILL')` for whatever is still alive; `SIGTERM`/`SIGINT`/`SIGHUP` to the main process (`installSignalHandlers`), a failed `main()` and `will-quit` do `close()` and `killAllSync('SIGTERM')` (the signals then `app.exit(0)`, no dialog). A SIGKILL or a power loss cannot be handled: the next start finds the leftovers. `OrgManager.init()` (and each `refreshHealth`, only while the file holds a line of an earlier run) calls `findLeftovers`: for lines whose pid is not a child of this run it runs `ps -ww -o pid=,etime=,command= -p <pids>` and keeps a line only when the process is alive, its command line contains `claude`, the word `-p` and `--permission-prompt-tool mcp__coa__permission_prompt` (tested as substrings, the rest of the line, which holds the mcp-config token, is never kept), and its start time (now minus etime) is within 10 s of `spawnedAt` (a reused pid fails this); other lines are pruned, and a line of an org that is not registered at the same path is kept but not reported. Leftovers go on that org's `HealthStatus.leftoverProcesses`; a green indicator turns yellow (label "Needs attention", no Sync button: `leftoverOnly` in `renderer/logic.ts`). The health popover lists each one (`LeftoverProcesses.tsx`: pid and start time) with "Stop" (`CoaApi.stopLeftoverProcess`): `stopLeftover` re-runs the checks for that org and pid (anything else is refused), sends SIGTERM to the group, SIGKILL after 4 s, and drops the line. The app never stops a process that is not in its own ledger.
- Supported Claude Code range: `SUPPORTED_CLAUDE` in `src/main/config.ts`, checked with `claude --version` at launch. Outside the range the app refuses to start sessions.

## Permission rules
- **The app does not decide what to allow.** Claude Code decides with its own parser and rules; the app's permission prompt tool (`mcp__coa__permission_prompt`) is only called for what Claude Code would ask. The app has no baseline of its own (no read-only list, no bare `Read`/`Grep`/`Glob`/`LS`): Claude Code already runs common read-only commands and reads inside the working folder without asking (plugin doc `gates/permissions.md`). There is no app-side parser that allows anything: a hand-written parser is bypassable (`$'..'` quoting, `VAR=x git diff`, a path in front of the program, `>&1x`, risky flags).
- **`--allowedTools`** = `ALLOWED_TOOLS` (`Skill(ceo-of-agents:*)`) + the hq's `permissions.allow` (`.claude/settings.json` and `.claude/settings.local.json`) that pass `filterAllowRules` (`src/main/claude/rules.ts`): a committed allow rule is a pre-approval, so bare tool names, wildcard-only or program-wide Bash rules (`python *`, `rm *`, exact-only programs), `mcp__*`, WebSearch, WebFetch without `domain:` and path rules outside the hq are dropped; the plugin's generated rules (`Edit(/**)`, `Read(~/.claude/plugins/cache/ceo-of-agents/**)`, `Bash(sh *check-boot-set.sh*)`, gh/git rules) pass. Dropped rules are listed in the hq health popover (`HealthStatus.droppedRules`, split into `local` and `project`; informational, never changes the indicator colour). "Clean up" (`CoaApi.cleanUpIgnoredRules(orgId)`, `removeDroppedLocalRules` in `rules.ts`) removes from `settings.local.json` only the allow rules `filterAllowRules` drops, recomputed in main after one inline confirm (atomic, other keys and rules kept, an error when the file is missing or invalid); it never reads or writes the committed `settings.json`, whose ignored rules change through the chief of staff. Deny rules are never filtered. **`--disallowedTools`** = the hq's `permissions.deny` + the user's own `permissions.deny` (sessions run with `--setting-sources project,local`, which drops the user's file; the app reads that one key from the same file used for mode and effort, `SettingsStore.userDenyRules()`). A path rule there that starts with a single `/` is anchored to the folder of the user settings file (`~/.claude`), as the Claude Code permissions docs say ("`/path`: relative to the settings source"; `Read(/secrets/**)` in user settings blocks `~/.claude/secrets/**`), and passed as `//abs`.
- **Path rules on the command line.** In a settings file `Edit(/**)` is relative to the file's folder; on the command line its meaning is not guaranteed. `anchorPathRule` (`src/main/claude/rules.ts`) rewrites Read/Edit/Write/MultiEdit/NotebookEdit/Grep/Glob rules whose argument starts with a single `/` into `Tool(//<absolute folder>/...)` (the hq folder for hq rules, the user settings folder for user rules). `//abs`, `~/`, relative and non-path rules are untouched.
- **Always allow proposals** (`ruleFor`, `validateRule`) are narrow: exact command only for dangerous programs, the exact-only set (`pnpm`, `yarn`, `cargo`, `go`, `make`, `swift`, `security`, `launchctl`, `defaults`, `tee`, `dd`, `tar`, `cp`, `mv`, `chmod`, `npm exec/x`), `git push/reset/clean/checkout/branch/remote`, and `cat/head/tail/rg/grep` with a path outside the hq; nothing for dotfiles outside the hq or for `.mcp.json`, `CLAUDE.md`, `AGENTS.md` anywhere.
- **The broker** (`PermissionBroker`): (a) a request matching a deny rule (hq or user, `isDenied`, which matches more than Claude Code does: safe direction) is denied with the rule in the message; (b) an exact repeat (same tool name, deep-equal input) of a request approved with "Always allow" in this app run is allowed; (c) everything else is shown to the user as a card. Allow once, Always allow, Deny.
- **"Always allow" proposals** (`ruleFor`): none (no "Always allow" button, no rule input) for a multi-line command, one over 200 characters, one with any of `$ \` ` > < ( )` or a backslash, a leading `VAR=`, a program given as a path, or an exact command holding `*`. A program that runs other programs (`bash sh zsh ... python* node env sudo xargs eval exec source . find sed awk rm docker kubectl ssh scp curl wget osascript open nohup time timeout watch`, also `npx bunx pnpx`) and `gh api`, `git -c`, `git config`, a git flag before the subcommand: the exact command `Bash(<command>)`. Anything else: `Bash(<program> <subcommand> *)` (Claude Code's documented space-star form; the older `:*` is only accepted when an edited rule uses it). Edit tools: the exact file, `Edit(/<path inside the hq>)` or `Edit(//<absolute path outside>)`, never a glob, and none for a path under `.claude/` or `.git/`. Read tools: none. `validateRule` rejects an edited rule that a proposal could not be (bare `Bash`/`Edit`, `Bash(*)`, prefix rules of the programs above, `Edit` globs, `.claude`/`.git`, a directory, multi-line, another tool); the broker then keeps the proposal, and with no proposal the answer is Allow once.
- **Artifact rules.** Claude Code matches an `Artifact` rule as `key:value` against the input, so the only shape is `Artifact(action:<a>)` (`Artifact(read)` is ignored by it). "Always allow" is offered only for `read`, `list` and `open` (`SAFE_ARTIFACT_ACTIONS`), as `Artifact(action:<a>)`; `publish`, `delete` and every other action have no proposal and always ask. `validateRule`, `allowRuleOk` and `filterAllowRules` accept exactly those three rules (a bare `Artifact`, wildcards and other actions are rejected or kept out of `--allowedTools`); a deny rule `Artifact(action:<x>)` (a trailing `*` is a prefix) matches that action, a bare `Artifact` deny matches every call. The app's filter only affects `--allowedTools`: sessions run with `--setting-sources project,local`, so Claude Code itself reads `permissions.allow` from `.claude/settings.json` and `settings.local.json` and would honour a broad `Artifact` rule (`Artifact`, `Artifact(*)`, `Artifact(action:*)`, any action but read/list/open) or any `AskUserQuestion` rule, running a publish, a delete or an answer with no card. The app cannot stop that, so `broadAllowRulesBySource` (`rules.ts`, `isBroadSelfAllowRule`) finds those rules in both files at each health refresh (also when the watcher sees either file change, `HqChange` `settings`) and `HealthStatus.broadRules` shows them in the health popover as a warning (listed apart from `droppedRules`, not counted there; informational, no colour change). "Clean up" removes them from `settings.local.json` only; the committed `settings.json` is never rewritten: the warning names the file and the rule and the fix goes through the chief of staff.
- **Settings window APIs.** `OrgManager.getPermissionRules(orgId)` returns the hq's allow list, the saved list and the deny list (`buildPermissionRules` in `src/main/claude/rule-lists.ts`; `dropped` comes from `filterHqAllowRules`, so it matches what sessions get; reads files only, so any org works). `OrgManager.removeSavedRule(orgId, rule)` removes exactly that rule from `permissions.allow` of `.claude/settings.local.json` (`removeSavedAllowRule`, atomic merge, no write when absent) and also clears the broker's in-run memory for it (`PermissionBroker.forgetRule(hqPath, rule)`), so an exact repeat of the request asks again; the chats pick the change up from the next message (`needsRestart`). Only saved rules can be removed in the app: rules in `.claude/settings.json` are the hq's and are changed there. `OrgManager.getAbout(orgId, appVersion)` (`src/main/org/about.ts`) gives the app, Claude Code, plugin and framework versions and the hq path from what the app already knows; nothing is fetched, unknown values are null ("Unknown" in the UI).
- **Rules apply from the next turn.** `OrgSession.runs` records the allow/deny lists (and the MCP lock and kept-out servers) a process was started with; `needsRestart` is also true when the lists that would be passed now differ (a rule written by "Always allow", a change in the hq's files, the user's deny rules), so the next message restarts the process with `--resume`. Never mid-turn.
- **Restarting with a card pending.** `restartSessions()` first denies this org's pending permission requests through the broker (`PermissionBroker.denyPending`, the thread keeps its registration) and adds a system line to the thread; it waits for each chat to go idle for at most 120 s (`restartWaitMs`), then stops it anyway.

## Connectors
- **Read only, never a direct grant.** `OrgManager.getConnectors(orgId)` (`readConnectors` in `src/main/hq/connectors.ts`, pure, never throws: an unreadable org.yaml is `error` on empty lists; works for any registered org, no activation) gives `ConnectorsInfo`: per department (org.yaml order) its `connectors` in org.yaml (`granted`), the `mcp__` entries of its agent file's `tools:` line (`inAgentFile`) and `advisory` (`from_catalog` legal, finance or tax); `forbidden` (`accounts.forbidden_connectors`), `forbiddenLocal` (accounts.local.yaml), `forbiddenProblems`, `forbiddenWarnings` (case mismatches); per department `toolsLine` (its agent file has a non-empty `tools:` line); `available`; and `session` (what the chats loaded, see below). Files are read up to 256 KB (`readCapped`). `connectors.ts` has no write path (a test checks its source).
- **What is read and what is not.** `available` is the server names (keys of `mcpServers`, matching `/^[A-Za-z0-9_.-]+$/`) of the hq's own `.mcp.json` as `mcp__<server>__*`, never any value inside it (commands, args and env may hold secrets); the file is read only when it is a regular file (`lstat`: a symlink or a folder is refused outright) whose real path is inside the hq's real path, else it counts as absent; minus the servers a forbidden pattern covers, from either file (`matchesPattern`: `*` matches any run of characters; a forbidden pattern that names a tool of the server also drops it). From accounts.local.yaml the app reads only `forbidden_connectors` and, of each item, only `pattern` (`readForbiddenPatterns` in `src/main/hq/forbidden-connectors.ts`: the file also holds local paths and account labels). The app never reads `~/.claude.json`, Claude Code's global state or the user's settings for connectors and never runs `claude mcp list` (it starts servers).
- **MCP as in the CLI.** App chats run without `--strict-mcp-config` (unless locked, below) and with `--setting-sources project,local` (checked live with Claude Code 2.1.327 and fake servers; fixtures `test/fixtures/claude/mcp-init-*.jsonl`, recording in `fake-mcp-server.mjs`). Loaded: the hq's `.mcp.json` servers (stdio and http), local-scope servers, claude.ai connectors. NOT loaded: user-scope servers (added with `claude mcp add -s user`): they need the `user` setting source, which also loads the user's hooks, permissions, env and enabled plugins, and the app keeps that out on purpose. Per-tool access as in the CLI: a department chat started with `--agent` is offered only the MCP tools in its agent file's `tools:` line (the three servers still connect); the chief of staff has no `tools:` line and goes by the permission rules and the permission prompt tool. An agent with no `tools:` line, or with a `*` entry (`tools: "*"`, `["*"]`, `Read, *`; `mcp__x__*` is not one), is offered every MCP tool of every loaded server (checked), hence the lock for it. The org.yaml `connectors` grants are no longer turned into server config: they stay the record of what a department is meant to use (the agent file does the enforcing). A server named in `--mcp-config` as `coa` is the app's own and is never listed as a connector.
- **Forbidden connectors.** Each pattern of both lists goes through `forbiddenDenyRule` (`*` is `mcp__*`; else it must start with `mcp__`; characters after it outside `[A-Za-z0-9_*-]` become `_`, as Claude Code does in tool names, so `mcp__claude.ai Example__*` becomes `mcp__claude_ai_Example__*`) and joins the hq's and the user's deny rules in `--disallowedTools` (deduped). A pattern that is not `*`, does not start with `mcp__`, has nothing after it or is over 200 characters is a problem, never dropped silently. **Problems** (`ForbiddenPatterns.problems` plus the rule problems, merged in `SessionDeny.problems`, shown in Settings): org.yaml missing, unreadable, over 256 KB, invalid YAML or not a mapping; `accounts` or `forbidden_connectors` of the wrong shape (null is an empty list); accounts.local.yaml (a missing or empty one is fine) unreadable, too big, invalid or of the wrong shape; a list item that is not a text or an object with a non-empty text `pattern` (named by file and 1-based position); a pattern that is no rule (quoted, cut to 80 characters). A problem text never holds another field of accounts.local.yaml. **MCP lock**: any problem, or a department whose agent file has no `tools:` line or has a `*` entry in it (`agentToolsLine` in `connectors.ts`, which returns `lock: 'no-tools-line' | 'all-tools' | null`: the file whose frontmatter `name` is the agent, else `<agent>.md`; missing, empty or unreadable file or line is `no-tools-line`), starts the process with `--strict-mcp-config` (`strictMcp` in `buildClaudeArgs`, right after the `--mcp-config` value) and `ENABLE_CLAUDEAI_MCP_SERVERS=false` besides all deny rules that could be built (checked 2.1.327 with fake servers and no sign-in, fixtures `mcp-init-strict-*`, `mcp-init-inline-strict`, `mcp-init-plugin-strict*`: under `--strict-mcp-config` only the app's `coa` loaded and only `mcp__coa__*` tools were offered, with or without `--agent`; the hq `.mcp.json`, local-scope, agent-frontmatter `mcpServers` and plugin `.mcp.json` (`--plugin-dir`) servers did not load. Claude.ai connectors under the lock (strict plus `ENABLE_CLAUDEAI_MCP_SERVERS=false`) were NOT recorded: that stays a live check with a signed-in account). Settings marks a locked department (`ConnectorDepartment.mcpLock`) with a "Connectors locked" badge and a line saying why. `OrgSession.runs` records the lock and the kept-out names per thread, so a change (a fixed file unlocks, a broken one locks) restarts an idle process with `--resume` (`needsRestart`), like a change in the rule lists. Deny rules remove tools; the server still starts. So `mcpLaunch(denyRules, keptOut, locked)` also keeps servers from starting: `deniedMcpServers` takes the REAL name (checked: `example_dotted` does not stop `example.dotted`, `example.dotted` does), computed once in `sessionDeny` (`keptOut`, the same list `getConnectors` shows as "Kept from starting"): a raw pattern that is exactly `mcp__<S>` or `mcp__<S>__*` gives S as written (`rawServerNames`); a deny rule naming a plain S gives the real name of the hq's `.mcp.json` server (or a raw name) whose tool prefix is `mcp__S`, else S. Never a claude.ai connector (`claude.ai ...` or `claude_ai_...`: real names cannot be derived and `deniedMcpServers` is unverified for them): their tools are still denied by the rule, and a rule covering all claude.ai connectors (`*`, `mcp__*`, `mcp__claude*`, `mcp__claude_ai_*`) sets `ENABLE_CLAUDEAI_MCP_SERVERS=false`. Deny matching is case-sensitive (checked: `mcp__EXAMPLE-PROJECT__*` removed nothing): `caseWarnings` gives `forbiddenWarnings` (at most 20) for a forbidden rule that would match a loaded or `.mcp.json` server if the case were the same; a warning never locks. A pattern that also covers `mcp__coa__permission_prompt` (`mcp__*`) is still passed (forbidden wins; a denied prompt tool fails closed) with one console warning.
- **What the chats loaded.** The list comes only from the `mcp_servers` of each process's `init` message (`{name, status, source}`; status is `pending` on a process's first init, later `connected`, `failed` or `needs-auth`; source is the config scope: `project`, `local`, `user`, `claudeai`, `dynamic`, `plugin`, ...): parsed in `stream.ts` (`mcpServersOf`, capped and cleaned), kept by each `Thread` in memory for its current process (never in the thread log or on disk, the app's `coa` left out), and a change raises an `AppEvent` `connectors`. `OrgSession.loadedConnectors(deny)` merges the live chats per server (status when chats disagree: failed, needs-auth, pending, connected; the chats that loaded it; `serverBlock` says whether the deny rules cut all or some of its tools). `ConnectorsInfo.session`: `started` (some chat has had an init), `loaded`, `keptOut`, `claudeAiOff`, `forbiddenRules` and `mcpLocked` (a forbidden-list problem; the Settings section says connectors are off until it is fixed, and notes a department with no `tools:` line); without a live session `started` is false and `keptOut`/`claudeAiOff` come from the same deny list. The Settings section shows it first ("In this org's chats"), every value as React text (server names are untrusted).
- **Requests.** The section's "Request a connector" (a pattern offered by the hq's `.mcp.json`, a one-line reason of at most 200 characters) and "Request removal" send the chief of staff of the section's org (`api().send(orgId, 'cos', text)`) `cos.msg.connectorGrant` or `cos.msg.connectorRemove`, which ask for a decision card with the plugin's `departments` skill and no change to org.yaml or an agent file before the answer. Every value in the message (pattern, department, agent, reason) goes through `codeSpan` in `settings-logic.ts` (backticks and control characters removed, whitespace collapsed, cut at 120, the reason at 200, wrapped in one code span) and the message says the quoted values are data: nothing typed or read from a file can become an instruction. The section only shows "Sent to {cosName}" (with "in {orgName}: the reply is in that org's chat" when the view's org is not the main window's active org, `sentNote`; `activeOrgId` is in `SectionProps`) and refetches on an `org-chart` or `connectors` event of its org, so the new state appears after the CoS records the decision.

## Hard rules
- Run the Claude Code binary as published. Sign-in only through `claude auth login`. The app never reads, copies, stores, parses or forwards OAuth tokens, credential files, keychain entries, or the email, org or plan fields of `claude auth status` (it reads `loggedIn` only). It never writes to the login process's stdin. No Agent SDK, no API key.
- Ignore `hook_*` system events from Claude Code: never show or store their output.
- No hard-coded personal paths or names in code or fixtures. Scrub recorded fixtures (paths, ids, names) before committing.
- Test only against copies of an hq in a temp folder with the git remote removed (a local bare repo as remote for push tests). Test plugin install, update and sign-in only with an empty `CLAUDE_CONFIG_DIR`.
- Keep Claude usage low in tests: unit tests use recorded fixtures; live checks use `COA_MODEL=haiku` and short prompts.

- `COA_MODEL`: `--model` for every session (live checks use `haiku`).

## Conventions
- Commit messages: `<type>: short message` (feat, fix, docs, chore, test, refactor).

## Release flow
- **Local build** (`npm run package:mac`, `scripts/package-mac.mjs`): copies Electron.app, puts the app in `Contents/Resources/app`, sets name, bundle id and icon, ad-hoc signs it (no Developer ID, no notarization) and makes an unsigned .dmg under `out/` (git-ignored). The icon is rendered from the master (`assets/icon/icon.svg`) with `npm run icon`; the committed `assets/icon/icon.icns` goes into the bundle.
- **CI** (`.github/workflows/release-mac.yml`, macOS arm64 runner):
  - A pushed tag `vX.Y.Z` runs: the tag must equal `version` in package.json (else the job fails), `npm ci`, the Electron binary, `npm run check`, `npm run package:mac`. A second job on Linux then creates the GitHub Release for the tag with generated notes and the asset `CEO-of-Agents-<version>.dmg`.
  - A manual run (Actions tab, or `gh workflow run release-mac.yml` once the workflow is on main) builds and keeps the .dmg as a workflow artifact for 7 days. It publishes nothing.
  - No secrets are used. The release job's token gets `contents: write` only.
  - macOS runner minutes count against the account's Actions quota, so the workflow has no push or pull request trigger.
- **Cutting a release** (maintainers only; publishing is always an explicit, manual step):
  1. On a branch, `npm version X.Y.Z --no-git-tag-version` (updates package.json and package-lock.json), open a PR, merge it.
  2. On an up-to-date main, `git tag vX.Y.Z && git push origin vX.Y.Z`.
  3. Watch the run in the Actions tab. The release appears under Releases.
- **In-app update** (`src/main/system/app-update.ts`, top bar button next to the plugin Update): a packaged app asks the user's `gh` (`gh release view --repo ceo-of-agents/ceo-of-agents-desktop`, 10 s timeout, cached 1 h) for the latest release and offers it when it is newer and carries `CEO-of-Agents-<version>.dmg`; gh missing, signed out or offline hides the button quietly. The click downloads with `gh release download`, mounts the .dmg read-only, checks bundle id and version against the running app, copies the app to a temp folder (`ditto`), detaches and runs `codesign --verify`; all of that BEFORE quitting and nothing is replaced on a failure. Then it calls `QuitCoordinator.request()` (Cmd+Q path: handover check, run guard). At exit a detached `/bin/sh` helper (script text in code, every value a positional argument) waits for the app's pid (if the app is still running after 60 s it gives up and deletes its temp folder), copies the new app to `<app>.new` next to the target (same volume), renames the old one to `<app>.old`, renames the new one into place and restores `<app>.old` on any failure (`.old` is deleted only after success; a run interrupted between the renames is repaired at the next start), relaunches only when the quit started by the button actually went through (a cancelled or queued quit installs later without relaunch), and deletes its temp folder. The download uses the exact release tag from the check. Trust in the downloaded bundle comes from the authenticated `gh release download` from the app's repo; `codesign --verify` on an ad-hoc signed bundle only proves integrity, not origin. A staged update also installs on a normal quit; macOS shutdown installs nothing. Dev (unpackaged) builds never check or replace anything; a translocated or read-only location is refused with a message. The app menu's "Check for Updates…" (after About) is a manual check: it forces the check (skips the 1 h cache, same path as the automatic one via `AppUpdater.checkNow`) and reports in a dialog that the app is up to date, that a version is available (Update / Later) or why the check failed (`gh` missing, not signed in, GitHub unreachable, no release with a Mac download; `classifyRelease` tells these apart), while the automatic check and the button stay quiet on failure. Unverified risk: replacing an ad-hoc signed bundle may reset macOS permission grants (Files and Folders, Automation) for the new copy; check by hand on the first real update.
- **Opening a downloaded build** (ad-hoc signed, not notarized): macOS Gatekeeper blocks the first open of an app downloaded with a browser.
  1. Open the .dmg and drag "CEO of Agents" to Applications.
  2. Open it once. macOS says it cannot be opened ("Not Opened"); choose Done.
  3. System Settings > Privacy & Security, scroll to Security, click "Open Anyway" next to "CEO of Agents" and confirm with your password. From then on it opens normally.
  - Alternative in Terminal, after copying the app: `xattr -dr com.apple.quarantine "/Applications/CEO of Agents.app"`.
  - A .dmg fetched with `gh release download vX.Y.Z -R ceo-of-agents/ceo-of-agents-desktop -p '*.dmg'` gets no quarantine flag (only browsers and similar apps set it), so the app opens without these steps.
